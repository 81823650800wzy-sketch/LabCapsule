# LabCapsule V0.10.0 统一桌宠：制作、安装与完整测试流程

本指南适用于 Windows 版 LabCapsule Studio V0.10.0。桌宠角色包采用“一个文件夹、一份身份、一个主形象”的原则。普通角色以同一 `avatar` 驱动 AI 主舞台、桌面悬浮宠物和屏幕工作室；Live2D 角色以同一 `live2dModel` 驱动独立 WebGL 主舞台和透明悬浮舞台。名称、人格和欢迎语随角色包一起切换。

本版本不要求修改 ESP32 固件、Android APK 或 Wi-Fi。把形象送往 240×320 屏幕工作室只是载入预览，不会自动覆盖设备上的现有壁纸；真正上传仍需要用户再次确认。

## 1. 最短使用路径

1. 准备一个 PNG、JPG、WebP、GIF，或完整的 Live2D Cubism runtime 文件夹。
2. 可直接把它单独放入一个文件夹；应用会把文件夹名作为桌宠名并自动生成本地身份。
3. 打开 `AI 桌宠 → 统一桌宠管理 → 选择桌宠 / 库文件夹`。
4. 既可选择这个桌宠文件夹，也可选择包含多个桌宠子文件夹的“桌宠库”。
5. 在下拉框选中桌宠，点击“应用所选统一桌宠”。
6. 检查 AI 主舞台，再打开桌面悬浮宠物，最后点击“将当前形象送到屏幕工作室”。三个位置应显示同一个形象。

只有一个图片文件或一个可识别 `model3.json` 的文件夹适合快速试用。需要长期保存、分发或加入 AI 人格时，请创建标准角色包。Live2D 第一次播放会显示许可说明，必须由用户本人阅读并勾选确认。

## 2. 标准角色包格式

```text
my-pet/
├─ pet.json
├─ avatar.png       # 也可以是 jpg、webp 或 gif
└─ persona.txt
```

`pet.json` 示例：

```json
{
  "$schema": "https://raw.githubusercontent.com/81823650800wzy-sketch/LabCapsule/main/docs/pet_package_v1.schema.json",
  "schemaVersion": 1,
  "id": "my-pet",
  "name": "我的桌宠",
  "avatar": "avatar.gif",
  "personaFile": "persona.txt",
  "greeting": "链路就绪。今天想观察什么现象？",
  "author": "作者名称",
  "license": "CC0-1.0",
  "homepage": "https://example.com/my-pet"
}
```

Live2D 包把 `avatar` 换成 `live2dModel`，两者只能存在一个：

```json
{
  "$schema": "https://raw.githubusercontent.com/81823650800wzy-sketch/LabCapsule/main/docs/pet_package_v1.schema.json",
  "schemaVersion": 1,
  "id": "my-live2d-pet",
  "name": "我的动态桌宠",
  "live2dModel": "live2d/my-pet.model3.json",
  "personaFile": "persona.txt",
  "greeting": "动作链路就绪。",
  "author": "模型作者",
  "license": "填写模型的真实许可证",
  "homepage": "https://example.com/model-license"
}
```

核心规则：

- `id` 只用小写字母、数字、点、下划线和连字符，最长 64 字符；同一个库内不能重复。
- `name` 为 1–24 个字符。
- `avatar` 是唯一主形象，不要为主界面、悬浮层和设备分别制作三个身份。
- `live2dModel` 指向 Cubism runtime 的 `.model3.json`；应用会继续校验其 `.moc3`、PNG 纹理、physics/pose/display-info、expression 和 `.motion3.json` 依赖。
- 图片支持 PNG/JPG/WebP/GIF，最大 12 MiB、2048×2048、每帧 4,194,304 像素、120 帧，总源像素不超过 180,000,000。
- `persona.txt` 必须是 UTF-8，最大 16 KiB；当前应用使用前 2,400 字符。
- 所有文件路径必须位于角色包文件夹内，禁止绝对路径和 `..` 跨目录引用。
- `author`、`license` 和 `homepage` 只记录真实来源与授权，不会自动赋予使用权。
- `.cmo3` 是编辑器模型，`.can3` 是编辑器动画；桌面播放器使用 `.model3.json` 和 `.moc3` 等 runtime 文件。文件含义以 [Live2D 官方说明](https://docs.live2d.com/en/cubism-editor-manual/file-type-and-extension/)为准。

机器可读规范见 [pet_package_v1.schema.json](pet_package_v1.schema.json)。

## 3. 使用仓库 Skill 创建桌宠

仓库内提供 `skills/labcapsule-pet-creator`。它包含制作说明、格式规范、测试清单和不会覆盖非空目录的创建/校验脚本。

直接使用脚本：

```powershell
cd <仓库目录>
python skills\labcapsule-pet-creator\scripts\create_pet_package.py create `
  --source "D:\Pictures\my-avatar.gif" `
  --output "D:\Pets\my-pet" `
  --id "my-pet" `
  --name "我的桌宠" `
  --persona "你是友善、严谨的 LabCapsule 实验伙伴，不编造传感器数据。" `
  --greeting "链路就绪。今天想观察什么现象？" `
  --author "作者名称" `
  --license "填写真实许可证" `
  --homepage "https://example.com/my-pet"
```

校验已有角色包：

```powershell
python skills\labcapsule-pet-creator\scripts\create_pet_package.py validate "D:\Pets\my-pet"
```

从一个 `.model3.json` 创建便携 Live2D 包（只复制运行时依赖，不复制 `.cmo3` / `.can3`）：

```powershell
python skills\labcapsule-pet-creator\scripts\create_pet_package.py create-live2d `
  --model "D:\Models\my-pet\runtime\my-pet.model3.json" `
  --output "D:\Pets\my-live2d-pet" `
  --id "my-live2d-pet" `
  --name "我的动态桌宠" `
  --license "填写真实许可证" `
  --homepage "填写模型条款网址"
```

成功时输出包含 `"valid": true`、尺寸、帧数和 SHA-256；失败时退出码为 2，并给出具体原因。创建命令拒绝覆盖非空目录。

如果希望 Codex 以技能方式调用，可把整个 `skills/labcapsule-pet-creator` 文件夹复制到 `%USERPROFILE%\.codex\skills\labcapsule-pet-creator`，重启 Codex 后使用：

```text
使用 $labcapsule-pet-creator，把这个 PNG/GIF 制作为统一桌宠角色包并完成校验。
```

## 4. 应用如何直接识别文件夹

“统一桌宠管理”支持两种选择：

- 选择角色包本身：文件夹顶层含 `pet.json`，或恰好只有一个支持的图片文件，或在有限深度内恰好识别到一个 `.model3.json`。
- 选择桌宠库：其第一层子文件夹分别是独立角色包；应用会扫描并列出全部有效桌宠。

应用启动和打开管理窗口时还会自动扫描：

```text
%APPDATA%\LabCapsule\pets\<桌宠文件夹>
<仓库根目录>\pets\<桌宠文件夹>
<EXE 所在目录>\pets\<桌宠文件夹>
```

标准角色包的选择会记录到 `%APPDATA%\LabCapsule\selected_pet.json`。下次启动重新校验原文件夹后再恢复，不复制第二份形象；文件丢失或失效时安全回退，不让应用崩溃。

## 5. 完整桌宠测试流程

以下每一步都给出预期结果。建议先完成 A–D，再根据条件执行 E–H。

### A. 角色包静态校验

1. 执行 `validate` 命令。
2. 确认输出的 `id`、`name`、文件格式、宽高、帧数和 SHA-256 与素材一致。
3. 把整个角色包移动到另一个目录后再次校验。

预期：两次均为 `valid: true`；移动后不依赖原素材路径。

再准备下列错误样本，逐个确认会被拒绝：

- `id` 含空格或大写字母；
- `avatar` 写为 `../outside.png`；
- 同一零配置文件夹放入两张图片；
- `persona.txt` 不是 UTF-8；
- 图片超过大小、尺寸或帧数限制。

预期：错误只影响对应角色包；扫描同一桌宠库时，其他有效桌宠仍会列出。

### B. 文件夹与桌宠库识别

1. 启动 `LabCapsule-Studio-0.10.0.exe`。
2. 进入“AI 桌宠”，点击“统一桌宠管理”。
3. 先选择单个角色包文件夹，确认下拉框只出现这个桌宠。
4. 再选择它的父级桌宠库，确认库中每个有效子文件夹各出现一次。
5. 选择目标角色并点击“应用所选统一桌宠”。

预期：状态行显示名称、ID、可选许可证和“三个舞台使用同一主形象”；主舞台立即更新，角色名、人格文本和欢迎语同步切换。

### C. 普通图片/GIF 的三处统一形象

1. 记录 AI 主舞台当前形象。
2. 点击“显示桌面悬浮宠物”，对照主体、颜色和动画。
3. 返回主窗口，点击“将当前形象送到屏幕工作室”。
4. 检查屏幕工作室显示的源文件路径和 240×320 预览。

预期：三个位置均来自 `pet.json` 的同一个 `avatar`；屏幕工作室允许裁剪/缩放，但这只改变设备画面的构图，不创建第二个桌宠身份。

Live2D 不执行此项的 ESP32 直传：240×320 设备无法直接运行 moc3。若要在设备屏幕使用同一角色，应先在已获授权的工具中导出/录制 GIF，再交给屏幕工作室裁剪和压缩。

### D. 重启、移除与回退

1. 正常关闭应用并重新打开。
2. 进入“AI 桌宠”，确认桌宠自动恢复。
3. 关闭应用，把角色包临时改名或移走，然后再次启动。
4. 恢复原文件夹后重新选择。

预期：正常重启可恢复名称、人格和形象；路径失效时回退到缓存网络形象或内置矢量形象，不出现空白窗口和崩溃；恢复文件后可以重新应用。

### E. GIF 动画时序

1. 使用含明显节奏的 GIF，至少观察两个完整循环。
2. 对照原文件的逐帧延时；当前桌面播放器把异常值钳制在 33–2000 ms/帧。
3. 打开/隐藏悬浮宠物，确认动画可持续播放。
4. 退出应用后重新打开，确认角色包 GIF 从本地文件重新加载。

预期：主舞台和悬浮层使用同一帧序列与时间轴；应用退出后当然停止运行，重新启动后无需手机后台传帧即可恢复。

### F. AI 身份与安全边界

1. 不填 API Key，询问“你叫什么、你的职责是什么”。
2. 检查回答是否采用当前角色名和人格，并保持本地规则回退可用。
3. 如有用户明确提供的测试 Key 或本地兼容 Mock，再测试在线模型。
4. 连接/断开设备或完成一次 Mock 实验，观察桌宠事件字幕。

预期：角色保持统一身份；没有 API Key 仍能回复；模型不能直接执行系统命令、修改 Wi-Fi、烧录固件或未经确认开始实验；日志不显示 API Key。

### G. 240×320 屏幕链路

1. 点击“将当前形象送到屏幕工作室”。
2. 在严格 240×320 预览中使用适应/填充、0.25–8 倍缩放、平移和黑/白补底。
3. 仅检查预览时不要点击上传。
4. 确实要替换设备当前媒体时，确认备份与构图后再手动上传。

预期：预览比例与实屏一致；选择桌宠不会自动写入 ESP32；上传仍走现有 USB CRC 与原子替换链路。

### H. COM8 与回归

仅查询设备而不改变状态：

1. 连接 COM8，确认串口为 460800 8N1。
2. 发送 `PING` 与 `STATUS`。
3. 记录固件标识、`READY`/错误状态、MPU、Mock、样本数、采样率与时长。
4. 不需要为桌宠角色包重刷固件，不要切换电脑 Wi-Fi。

开发者自动化回归：

```powershell
cd <仓库目录>
python -m unittest discover -s tests -v
python -m py_compile desktop\avatar_assets.py desktop\pet_packages.py desktop\labcapsule_desktop.py
python $env:CODEX_HOME\skills\.system\skill-creator\scripts\quick_validate.py skills\labcapsule-pet-creator
```

### I. Live2D / Hiyori 完整动态测试

本机样本目录：`<Live2D模型目录>`。它包含 Free 和 Pro 两个模型；选择父目录时，应用应列出：

```text
hiyori_free/runtime/hiyori_free_t08.model3.json  → 8 个动作
hiyori_pro/runtime/hiyori_pro_t11.model3.json    → 10 个动作
```

测试顺序：

1. 打开“AI 桌宠 → 统一桌宠管理”，选择 `<Live2D模型目录>`。
2. 下拉框应分别出现 Free 与 Pro，且标注 `Live2D · 8/10 动作 · 自动识别`；出现两个模型不是冲突，因为它们位于两个独立子包。
3. 先选择 Free，点击“应用所选统一桌宠”。首次会出现 Cubism 运行时说明。
4. 由用户本人打开并阅读文件类型、SDK 许可和 Expandable Application 页面；确认模型条款后再勾选并点击“确认并启动”。自动化测试不得替用户勾选。
5. 独立舞台应显示 Hiyori，而不是静态截图；底部状态应显示 WebGL 就绪和 8 个动作。
6. 逐一点击动作组按钮；点击模型身体区域，确认能触发 hit motion；拖动窗口边缘，确认模型保持居中并等比适配。
7. 回到主应用点击“显示桌面悬浮宠物”，确认透明、置顶的第二舞台能动；再次点击应关闭悬浮舞台，不影响主舞台。
8. 关闭主应用，确认所有 Live2D 子窗口随之终止。重新启动后，已保存的角色包和许可版本匹配时应自动恢复；若官方 Core URL/版本策略改变，则必须重新确认。
9. 对 Pro 重复 3–7，预期动作数为 10。
10. 断网测试：模型文件不会丢失或上传，但因 LabCapsule 不分发 Cubism Core，首次/未缓存的 WebView 可能无法启动。恢复网络后重试即可。

安全与许可边界：Hiyori 样本只用于当前电脑的开发验证，不复制到 Git 仓库、安装包或 GitHub Release。LabCapsule 使用本机 `127.0.0.1` 临时服务器提供模型依赖，不监听局域网接口。允许用户选择任意模型的正式产品可能属于 Expandable Application，发布前应再次依据 [SDK 许可](https://www.live2d.com/en/sdk/license/)和 [Expandable Application 指引](https://www.live2d.com/en/sdk/license/expandable/)核对。

## 7. 常见问题

### 选择文件夹后没有桌宠

检查图片是否在所选文件夹顶层。零配置模式必须恰好有一张支持图片；多图文件夹必须添加 `pet.json` 指定 `avatar`。选择桌宠库时，角色包应位于第一层子目录。

### 应用提示路径越界

`avatar` 或 `personaFile` 只能填写角色包内部的相对路径。不要填写盘符、网络路径或 `../`。

### GIF 不动或过慢

先用 `validate` 检查是否确实包含多帧。桌面端尊重源 GIF 延时，不使用设备端 1–8 FPS 壁纸速度设置；异常短帧最低按 33 ms，异常长帧最高按 2000 ms。送到设备后的帧率由屏幕工作室导出设置决定。

### 选到 Hiyori 父目录但提示有多个模型

选择 `hiyori_zh-Hans` 时，Free 与 Pro 应作为两个子角色分别列出。若直接选择一个同时递归包含多个 `model3.json` 的非库子目录，应用会拒绝猜测；请选择更具体的 `hiyori_free` / `hiyori_pro`，或创建带 `pet.json` 的标准包明确指定 `live2dModel`。

### Live2D 舞台空白或提示 Core 加载失败

先确认电脑仍连接正常互联网，且 WebView2 能访问 Live2D 官方 Core 地址。应用不会切换 Wi-Fi，也不会把模型上传到外部服务器。模型依赖缺失、纹理不是 PNG、路径越界或 JSON 损坏会在启动前被拒绝；网络/Core 问题则显示在舞台状态栏。

若旧测试包提示 `Current environment does not allow unsafe-eval`，这是 V0.10.0 首次候选包缺少 Pixi 严格 CSP 兼容层，不是模型损坏。使用最终 V0.10.0 包；它将 `pixi.js` 与 `@pixi/unsafe-eval` 同时固定在 6.5.10，并保持 CSP 不包含 `unsafe-eval`。不要通过关闭 CSP 或安装来源不明的 Core 绕过错误。

若窗口停在“正在校验并载入 Cubism 模型”且系统显示未响应，请先确认使用最终 V0.10.0 包。首次候选源码曾把原生 pywebview Window 暴露到 JS API，引起 Windows AccessibilityObject 递归；最终版只暴露关闭方法。正常启动后底部必须在数秒内显示 `WebGL 就绪`，否则按状态栏原始错误排查，不要把空白舞台判为成功。

### 角色名变了但回答人格没变

确认 `personaFile` 指向 UTF-8 `persona.txt`，应用角色包后再开启新对话。已有对话是有界历史，不会被篡改；必要时使用“清除桌宠记忆”重新测试。

### 从网络下载的形象能否自动成为标准角色包

网络形象仍可直接使用，但它只替换形象。需要可移植的统一名称、人格、欢迎语和授权信息时，请先保存合法来源的本地文件，再用仓库 Skill 创建标准角色包。
